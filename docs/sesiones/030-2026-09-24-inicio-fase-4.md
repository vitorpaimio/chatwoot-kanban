# Sessão 030 — Início da Fase 4

Pedido: começar a Fase 4. Preservadas as alterações não commitadas das fases
anteriores. Implementado pacote `installer` com `install --dry-run`, inspeção
Swarm/rede/container e inventário Rails somente leitura das contas selecionadas.
Plano reaproveita o catálogo da Fase 2 e não serializa conteúdo remoto arbitrário.

Testes: Ruff aprovado, 129 testes Python aprovados no PostgreSQL exclusivo e dois
opt-in omitidos; quatro testes Node aprovados. A primeira tentativa de pytest
foi impedida pela restrição de rede do sandbox; execução autorizada fora dele
passou. Não houve falha funcional nesse gate.

Não havia Docker neste Mac. O mantenedor considerou VPS com Hermes e depois
solicitou instalar Docker localmente. Instalados Docker CLI 29.8.1, Compose 5.5.1, Buildx 0.37.1 e Colima 0.10.3.
VM `kanban-phase4`: ARM64, 4 CPUs, 6 GiB RAM, disco de dados de 40 GiB, sem
montagens do host. Contexto ativo `colima-kanban-phase4`, Engine 29.5.2.
Swarm de nó único Ready/Leader e rede overlay `network_public` criados.
`hello-world` executado; serviço Nginx temporário com 2/2 réplicas respondeu
HTTP 200 dentro da VM e foi removido. Portas ingress do Swarm não foram
encaminhadas automaticamente para localhost do Mac; acesso do futuro proxy
precisa de publicação em modo host ou túnel explícito, ainda a validar.

A inicialização demorou cerca de três minutos: DNS/cloud-init falharam na primeira
passagem, mas o provisionamento posterior do Colima recuperou DNS e Docker, ambos
confirmados ativos. Não alteradas as configurações do macOS para contornar isso.

Inventário Rails executado também no Chatwoot local real: duas contas, com nove e
quatro definições, em transação somente leitura. Essa prova não certifica ainda
o comando completo contra Chatwoot dentro de Swarm.

Próximos passos: validar o dry-run no Chatwoot do Swarm descartável e implementar
backup/restauração, manifesto, usuário de serviço, deploy, sondas e comandos
mutáveis. Fase 4 iniciada, não concluída. ADR-035 registra as decisões e os limites.

## Continuação — Chatwoot oficial no Swarm

A pedido do mantenedor, instalada a imagem pública mais recente: Chatwoot CE
4.18.0, release publicada em 18/09/2026, confirmada pela API oficial do GitHub.
`latest-ce` do Docker Hub coincide com o digest fixado no template do laboratório.

Stack `cwlab`: PostgreSQL 16/pgvector, Redis 7, Rails, Sidekiq e Traefik.
Banco preparado com `rails db:chatwoot_prepare` (tarefa concluída); secrets gerados
em memória e enviados por stdin ao Swarm. Imagem e código do Chatwoot intactos.
Proxy em modo host resolveu o acesso pelo Mac: http://localhost:18080/api com 200
e tela de configuração inicial aberta no navegador. Nenhum usuário humano criado;
o mantenedor pode definir seu primeiro administrador nessa tela.

Template e instruções em `deploy/lab/`. Instância existente em localhost:3000 e
banco do Kanban preservados. Esta entrega prepara o laboratório; não conclui
instalação/desinstalação do Kanban nem a certificação completa da Fase 4.

Validação da continuação: `/api` confirmou versão 4.18.0, `queue_services=ok` e
`data_services=ok`; Rails/PostgreSQL/Redis saudáveis, um processo Sidekiq registrado
no Redis. Ruff, configuração da stack, sintaxe shell, 129 testes Python (dois
opt-in omitidos), quatro testes Node e `git diff --check` aprovados.

## Continuação — conta criada e Kanban operacional

Após o mantenedor criar sua conta, construída imagem Kanban local e instalada a
stack `kblab` (PostgreSQL, API e worker), com Alembic até head. Corrigida ambiguidade
do alias `postgres` entre as redes pela referência explícita `kblab_postgres`.
Backup Chatwoot cifrado antes das mutações; restauração real em banco temporário
passou e preservou a conta humana. O banco de prova foi removido.

Usuário técnico dedicado limitado à conta 1, senha aleatória compatível com a
política da 4.18.0 e token transferido somente em memória até cifragem no Kanban.
Loader e usuário têm manifesto no Chatwoot. Worker ativou a conta e registrou
três atributos obrigatórios e um webhook próprios. Sem importação de contatos.
Callback interno configurável foi necessário para a topologia Docker local;
origem pública da sessão/CSRF preservada. API e worker ficaram saudáveis.

Navegador com sessão humana real: Pipeline visível, funil principal com cinco
etapas, quadro vazio e atualização em tempo real conectada. Restauração do backup
comprovada; comandos genéricos de ciclo de vida continuam pendentes.
Ruff, 130 testes Python (dois opt-in omitidos), quatro Node e sintaxes shell/Ruby
aprovados. Sem commit, push ou publicação de imagem.

Repetição da ativação conferida: um usuário técnico, um manifesto, quatro recursos
e conta ainda pronta. Métricas carregaram normalmente na sessão humana; quadro
foi deixado aberto para o mantenedor.
